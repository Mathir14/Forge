# ADR-014: Machine Protocol Semantics, STATUS Definition, and Orchestration Invariants

**Status:** Approved  
**Author:** Forge Architecture & Engineering  
**Date:** 2026-09-23  
**Target Version:** Forge 1.1.0  
**Supersedes/Extends:** Refines Common Agent Protocol v1.0 and Stage Orchestration  

---

## 1. Context & Incident Analysis (The run-012 Failure)

During an autonomous execution run (`run-012`) against the target workload repository `career_intelligence_platform`, the pipeline experienced an unrecoverable protocol conflict that halted autonomous execution prematurely:

```
[0/6] Codebase Critic completed | Status: CRITIQUE_COMPLETE
[1/6] Invoking Architect (opencode) for task: "Implement moderation queue..."
  ✓ Architect completed | Status: BLOCKED
⚠️ Autonomous loop halted: Architect finished with status 'BLOCKED'.
```

### 1.1 Root Cause Analysis

Inspection of the machine report generated by the Architect revealed contradictory signals:
```yaml
ROLE: ARCHITECT
STATUS: BLOCKED
HANDOFF: PLANNER
ISSUES:
  CRITICAL:
    - "Pre-existing TypeScript typecheck errors in auth.ts"
    - "Demo admin credentials committed in seed script"
    - "Missing per-IP sign-in rate limiting"
NEXT_ACTION: "Remediate Critical #1–#3 before planning."
```

Simultaneously, the Architect had produced a comprehensive, high-quality, 7-module architecture specification (`01_architect.md`) defining the 4 required interfaces and complete component boundaries for the task.

However, the pipeline halted because:
1. The Architect evaluated the pre-existing health of the codebase, determined that the repository had pre-existing critical issues that prevented immediate production deployment, and labeled its outcome `STATUS: BLOCKED`.
2. Simultaneously, knowing that these issues could and should be remediated by downstream engineers, the Architect set `HANDOFF: PLANNER`.
3. The Forge orchestrator (`auto_pipeline`) treats `BLOCKED` as an immediate, terminal obstruction to autonomous execution, halting the pipeline without invoking the Planner.

This revealed a fundamental ambiguity in Forge's protocol contract:
- Does `STATUS` describe the validity of the artifact produced by the current stage, or the production readiness of the repository?
- What does `BLOCKED` signify? Is it an external operational blocker, or internal repository debt?
- Can a stage claim to be blocked from further progress while simultaneously routing to the next stage?

---

## 2. Decision & Fundamental Protocol Contract

We resolve this ambiguity by establishing strict protocol semantics and validation invariants without introducing extraneous protocol fields.

### 2.1 Authoritative Definition of `STATUS`

`STATUS` authoritatively answers:
> **"Did this role successfully complete its own responsibility?"**

- `STATUS` describes the validity and completeness of the artifact produced by the current stage.
- `STATUS` does **NOT** describe the health or production-readiness of the pre-existing repository.
- Role-specific semantics:
  - **Architect:** `STATUS: APPROVED` means: *"The architecture specification is complete, sound, and ready for planning."* It does **not** mean the repository is production-ready.
  - **Planner:** `STATUS: READY` means: *"The implementation plan and task decomposition are complete and ready for execution."*
  - **Executor:** `STATUS: SUCCESS` means: *"The requested implementation was completed and verified locally."*
  - **Tester:** `STATUS: PASS` means: *"Observable runtime behavior and user journeys succeeded."*
  - **Reviewer:** `STATUS: APPROVED` means: *"The implementation satisfies review criteria and code changes are sound."*
  - **Critic:** `STATUS: CRITIQUE_COMPLETE` means: *"The audit critique and health assessment are complete."*

Pre-existing repository defects (broken CI, red tests, security vulnerabilities, missing rate limiting, debt, bugs) are **implementation work**. They do not prevent the Architect from completing an architecture specification; rather, they become explicit architectural findings and remediation tasks to be planned and executed.

### 2.2 Strict Reservation of `BLOCKED`

`BLOCKED` is reserved exclusively for **external operational blockers**:
> **"The autonomous pipeline cannot make further progress because of an external dependency outside the repository."**

- **Valid uses of `BLOCKED`:**
  - Required API keys, tokens, or secrets missing from the environment.
  - External authentication or credential access required.
  - Required external specification or upstream documentation unavailable.
  - Repository or remote service completely inaccessible.
  - Database, cache, or external network infrastructure unreachable.
  - Headless browser or testing harness unavailable on the host OS.
  - Ambiguous or contradictory requirements requiring a human policy decision.
- **Strictly Invalid uses of `BLOCKED`:**
  - Security vulnerabilities or credential leaks in code.
  - Failing CI, linters, or typecheckers.
  - Red unit, integration, or E2E tests.
  - Missing rate limiting or performance bottlenecks.
  - Architectural debt or anti-patterns.
  - Implementation bugs or missing features.

All internal repository issues flow forward through the autonomous pipeline:
$$\text{Architect} \longrightarrow \text{Planner} \longrightarrow \text{Executor} \longrightarrow \text{Tester} \longrightarrow \text{Reviewer}$$

### 2.3 Unification of `REJECTED` Semantics

`REJECTED` has exactly **one** meaning across the entire Forge system:
> **"The task or objective itself is fundamentally inadmissible."**

- **Valid uses of `REJECTED`:**
  - The task requested by the user violates repository ADRs or security policies.
  - The task is logically impossible or internally contradictory.
  - The objective is fundamentally invalid or out of scope.
- **Consequence:** The autonomous pipeline terminates immediately (`HANDOFF: NONE`).
- **Defective Code is NOT Rejected:** Flawed or failing implementation code produced by Executor is **not** task rejection. It is handled by:
  - `CHANGES_REQUIRED` (Reviewer) $\rightarrow$ routes back to `HANDOFF: EXECUTOR` or `HANDOFF: ARCHITECT`.
  - `FAIL` (Tester) $\rightarrow$ routes back to `HANDOFF: EXECUTOR`.

## 3. Protocol Invariants & Validator Rules

To guarantee that the orchestrator never faces contradictory signals, `MachineReportValidator` strictly enforces the following invariants:

| Invariant | Rule | Violation Behavior |
|---|---|---|
| **Blocked Invariant** | `STATUS == BLOCKED ⇔ HANDOFF == NONE` | Error: `BLOCKED` with any non-`NONE` handoff is rejected. |
| **Inadmissible Task Invariant** | `STATUS == REJECTED ⇔ HANDOFF == NONE` | Error: `REJECTED` with any non-`NONE` handoff is rejected. |
| **Intermediate Routing Invariant** | Non-terminal success (`APPROVED`, `READY`, etc.) requires active downstream routing (`HANDOFF != NONE`). | Error: Architect or Planner emitting success with `HANDOFF: NONE` is rejected. |

### 3.1 Stage-by-Stage Status and Handoff Contract

```
┌──────────────┬────────────────────────┬─────────────────────────┬───────────────────────┐
│ Stage        │ Success (Continue)     │ Rework (Retry)          │ Terminal (Halt)       │
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Critic (Pre) │ CRITIQUE_COMPLETE      │ N/A                     │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: ARCHITECT/PLAN│                         │                       │
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Architect    │ APPROVED               │ N/A                     │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: PLANNER       │                         │ REJECTED(HANDOFF:NONE)│
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Planner      │ READY                  │ N/A                     │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: EXECUTOR      │                         │ REJECTED(HANDOFF:NONE)│
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Executor     │ SUCCESS                │ FAILED (Retry)          │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: TESTER/REVIEW │ HANDOFF: EXECUTOR       │                       │
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Tester       │ PASS / NOT_TESTABLE    │ FAIL / CHANGES_REQUIRED │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: REVIEWER/NONE │ HANDOFF: EXECUTOR       │                       │
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Reviewer     │ APPROVED               │ CHANGES_REQUIRED        │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: NONE          │ HANDOFF: EXECUTOR/ARCH  │ REJECTED(HANDOFF:NONE)│
├──────────────┼────────────────────────┼─────────────────────────┼───────────────────────┤
│ Critic (Post)│ CRITIQUE_COMPLETE      │ N/A                     │ BLOCKED (HANDOFF:NONE)│
│              │ HANDOFF: NONE          │                         │                       │
└──────────────┴────────────────────────┴─────────────────────────┴───────────────────────┘
```

### 3.2 StageOrder vs. HANDOFF Semantics (Execution Model)

To avoid ambiguity for future contributors, the relationship between `StageOrder` and `HANDOFF` is explicitly specified:
1. **`StageOrder` Drives Execution:** The autonomous pipeline sequence is authoritatively driven by `StageOrder` (`critic` $\rightarrow$ `architect` $\rightarrow$ `planner` $\rightarrow$ `executor` $\rightarrow$ `tester` $\rightarrow$ `reviewer` $\rightarrow$ `critic`).
2. **`HANDOFF` is Descriptive and Validating, Not Executable:**
   - `HANDOFF` expresses the agent's intended routing and serves as a strict contract validation invariant (preventing invalid combinations like `BLOCKED` with active handoffs, or `APPROVED` with `NONE`).
   - `HANDOFF` provides human and machine observability in logs, metadata, and reports.
   - `HANDOFF` does **not** dynamically override or divert stage transitions in the current Forge CLI orchestrator.
   - Future extensions (e.g., dynamic DAG scheduling) may consume `HANDOFF` for dynamic routing, but today orchestration control flow is governed exclusively by `StageOrder` and `STATUS`.

## 4. Consequences & Migration

1. **Resolution of run-012 Failure Mode:** Under ADR-014, an Architect analyzing a repository with pre-existing issues produces `STATUS: APPROVED` with `HANDOFF: PLANNER`, including the critical issues in the report architecture findings. The pipeline advances smoothly to Planner, which schedules remediation tasks for Executor.
2. **Deterministic Orchestration:** `MachineReportValidator` guarantees that `STATUS` and `HANDOFF` can never contradict each other. The orchestrator never has to heuristic-guess which field takes precedence.
3. **Fail-Closed Safety:** If an agent model ever emits an invalid combination such as `(STATUS: BLOCKED, HANDOFF: PLANNER)`, the validator marks `is_valid: False` with descriptive diagnostic errors, preventing unintended execution.

---

## 5. Protocol Stability

The machine-report protocol defined by ADR-014 is considered stable.

Future protocol changes should only be made when:

- they resolve a demonstrated production issue,
- they enable a clearly defined new capability,
- or they preserve backward compatibility while extending functionality.

Avoid semantic redefinition without empirical evidence from real-world usage.
