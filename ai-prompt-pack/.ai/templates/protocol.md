# Common Agent Protocol v1.0

Every agent MUST emit EXACTLY ONE machine report per response.

## Fundamental Protocol Contract (ADR-014)

### Definition of STATUS
STATUS authoritatively answers: "Did this role successfully complete its own responsibility?"
- STATUS describes the validity and completeness of the artifact produced by the current stage.
- STATUS does NOT describe the health or production-readiness of the pre-existing repository.
- Example: Architect emitting STATUS: APPROVED means the architecture specification is complete and ready for planning. It does NOT mean the codebase is free of defects. Pre-existing repository defects (failing CI, bugs, security debt) are implementation work to be remediated downstream.

### Allowed Statuses and Semantics
- Success Outcomes (APPROVED / READY / SUCCESS / PASS / CRITIQUE_COMPLETE): The stage artifact is valid and complete. Active routing is required for intermediate stages.
- Rework Outcomes (CHANGES_REQUIRED / FAIL): Reviewer or Tester identified implementation issues. Active routing back to rework stage is required.
- Terminal Operational Blockers (BLOCKED): Reserved exclusively for external operational dependencies outside the repository (missing API keys, authentication needed, external network/database unreachable, missing browser test harness on OS). NEVER use BLOCKED for internal repository issues (broken CI, red tests, security vulnerabilities, missing rate limiting, debt, bugs) — those are implementation tasks that flow downstream. STATUS: BLOCKED strictly requires HANDOFF: NONE.
- Terminal Inadmissible Tasks (REJECTED): The task itself is fundamentally inadmissible (violates repository ADRs, impossible request, invalid objective). Pipeline halts. STATUS: REJECTED strictly requires HANDOFF: NONE. Do NOT use REJECTED for defective code (use CHANGES_REQUIRED or FAIL).

Requirements:
- Emit EXACTLY ONE ```yaml fenced block.
- Emit EXACTLY ONE YAML document.
- Emit EXACTLY ONE ROLE field.
- Emit EXACTLY ONE STATUS field.
- Emit EXACTLY ONE HANDOFF field.
- Do NOT emit a second protocol block.
- Do NOT repeat ROLE, STATUS or HANDOFF.
- Additional role-specific information (ARCHITECTURE, MODULES, NEW_INTERFACES, etc.) must be additional YAML keys inside the SAME YAML document.
- Universal Scalar Quoting Rule: Every YAML scalar whose value is generated by the language model MUST be enclosed in double quotes unless the value is intentionally a numeric type, boolean, null, empty collection, or controlled enum (such as STATUS: READY, EXIT_CODE: 0, TASK_COUNT: 13, SUCCESS: true, DEPENDENCIES: []).
- All other generated values MUST be double-quoted: description: "...", reason: "...", summary: "...", component: "...", next_action: "...", evidence: "...", as well as task IDs, paths, commands, and list items.
- If a string contains inner quotes, use single quotes (e.g. 'inner text') or escape with a backslash (\"). NEVER use doubled double-quotes ("") inside a double-quoted YAML string.
- Never emit unquoted plain scalars for free-text or values containing colons, commas, brackets, braces, or hyphens.
- REASON is strictly for concise machine signaling, not human explanation. It must always be enclosed in double quotes as a single-line summary (maximum 100 characters). Detailed analysis, narrative rationale, and evidence belong in the Human Report, NEVER in REASON.
- The entire block must be parseable by yaml.safe_load().

Base Protocol Schema:
```yaml
ROLE:
PROMPT_VERSION: 1.0
TASK_ID: "task-001"

START_TIME: "2026-09-20T10:00:00Z"
END_TIME: "2026-09-20T10:05:00Z"
DURATION: "300s"

STATUS: READY
EXIT_CODE: 0
HANDOFF: NONE
REASON: "Concise single-line summary (max 100 chars)"

INPUTS: []
OUTPUTS: []

ISSUES:
  CRITICAL: []
  MAJOR: []
  MINOR: []

CONFIDENCE: HIGH
NEXT_ACTION: "Concise next action summary"
```
